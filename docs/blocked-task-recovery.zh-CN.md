# blocked 任务恢复

本文说明 Coordinator 对 `blocked` 状态的恢复语义、操作边界与升级注意事项。完整状态机仍以 `internal/orchestrator/state_machine.go` 为准。

## blocked 不再等于永久终止

`blocked` 表示当前这一轮执行已经结束，但任务本身仍可能继续。恢复不会复用旧 Run，也不会把旧执行当作成功：Coordinator 在原 Task 上执行一次原子、可审计的受理，把 Task 置回 `pending`，之后由普通调度器创建新一代 Run。

- 原 Task 身份、依赖、交付分支和上下文保留。
- 历史 Run、结果提交和错误证据保留，不会被覆盖。
- 每个恢复轮次使用新的 `recovery_generation`；累计 `attempt_count` 继续保留，另记录本轮基线和上限。
- 恢复受理记录包含操作者、理由、风险确认、来源 Run、代次和失败快照摘要。

## 三种操作展示

Task 详情页只对 `blocked` 任务展示恢复控件：

1. **可恢复**：暂时故障或已补齐的前置条件。按钮为“恢复任务”，直接受理。
2. **不可恢复**：`fatal` 分类、未满足的前置条件或存在安全阻塞。界面只显示原因和阻塞项，不提供“强制恢复”。
3. **未知风险恢复**：失败原因无法可信判定。按钮为“风险恢复”，必须勾选固定风险说明并填写理由；系统不会把 unknown 当作 fatal，也不会因确认风险而跳过执行、交付、写回、停止或 head 安全检查。

安全门包括但不限于：持久停止请求、仍活跃或无法证明退出的执行、未闭合的结果提交/写回/效果、非法仓库或 PR/MR head、未闭合的 finalization。未知风险确认只能覆盖“原因未知”，不能覆盖这些门。

## 权限与审计

- `member` 和 `tenant_admin` 可在本组织内向 blocked 任务发起恢复；这是 member 的单项任务权限，不授予停止、rebind、scheduler tick 等管理权限。
- 跨组织请求按不存在处理，不回落平台库。
- 恢复记录写入 Task 时间线；Task API 同时暴露累计尝试次数、本轮已耗次数和本轮上限，不把二者混称。

## 旧数据与预算

旧任务的 `recovery_generation` 为 0，仍按旧行为处理。第一次恢复后进入代次 1；旧执行结果、旧 token 回传和旧外部动作在代次不匹配时被拒绝或仅作为观测记录，不能推进新轮。

恢复轮次有独立预算上限。达到本轮上限后即使仍为 `blocked` 也不会自动再次派发；需要人工重新评估。

## 多实例升级

1. 先停止所有 Coordinator 的调度入口（`scheduler/tick`），确认没有正在收口的结果或外部动作。
2. 统一升级全部 Coordinator 和 Runner；不要保留旧版本实例与新 schema 混跑。
3. 启动时 schema 迁移会新增恢复相关列和表；迁移前先备份平台库/租户库。
4. 旧版本回滚不能安全读取新恢复记录；回滚前必须停调度并评估未完成恢复。恢复记录和代次字段不支持降级复用。
5. 升级完成后先用一个 blocked 任务验证“资格查询 → 恢复受理 → 新 Run”链路，再恢复调度。
